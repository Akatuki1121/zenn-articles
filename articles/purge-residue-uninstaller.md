普通のアンインストールはインストーラーが知っている範囲のものしか消さない。インストールのあとに生まれた設定は消す側の視界の外にある。別の仕組みへ登録された項目も同じだ。だから、アンインストールが終わったあとにもレジストリの値やサービスの登録やタスクスケジューラの項目が残る。この記事ではそれらを一つの画面で横断して探す道具を作ったときの設計を書く。

探すときの軸はアプリの名前ひとつにした。レジストリとサービス、タスクスケジューラと環境変数のPATH、スタートアップまで同じ名前で横断する。重いときだけMFTのファイル検索も使う。結果は種類を混ぜずに返す。種類ごとに置き場所も消し方も違う。使う側が種類ごとに判断できる形にしたかった。

検出と削除は分けている。探す側は検出だけを行い、削除はしない。削除は呼び出す側の責任だ。消す判断を機械の側で済ませたくなかった。見つけた順に消すのでもない。まず全部の候補をそろえてから扱う。候補がそろって初めて消してよいものと残すべきものの境目が見える。

境目の扱いでいちばん神経を使ったのは確からしさの付け方だ。レジストリとスタートアップは中程度で、それ以外は低い確からしさで返す。名前の一致で探す以上、別物の名前に当たることがある。確からしさが低いものほど使う側の目で確かめてもらう前提になる。確からしさを付けるのは機械が自信のあるふりをするためではない。判断を人に返すためだ。

レジストリの探し方はアンインストールのキーに限らない。HKCUとHKLMの主要な場所を文字列の一致で横断する。深い探索は重くなるので、代表的な場所に絞っている。Uninstallキーにしか目を向けなければ設定として残った値は見つからない。探す範囲を広げる代わりに深さには上限を置いた。速さと網羅のあいだで使う側が待てる形に寄せた。

どのアプリのものか分からなくなったフォルダは別の探し方をした。Program FilesとProgram Files (x86)、AppDataのRoamingとLocalの直下を棚卸しする。いま入っているどのアプリにも結びつかないフォルダを候補に出す。

結びつかないかどうかの判定はインストール先の完全一致だけでは弱い。多くのアプリがインストール先を登録していない。フォルダ名と表示名の表記ゆれもある。だから、表示名と発行元、インストール先とアンインストール文字列のそれぞれの階層から既知の名前を全部集める。候補のフォルダ名がどれか一つにでも部分一致すれば除外する。Windowsや開発環境が正規に使う名前もあらかじめ除外の一覧に入れてある。

候補にはフォルダの中のファイル数と合計の大きさを添える。いちばん新しいファイルの更新日も添える。最近更新されているフォルダはまだ使われている可能性がある。数字だけでは決められないが、目安がなければ判断は進まない。開発中の自分のパソコンで数えたら候補は48件あった。判定と除外の決まりを見直して25件まで減らした。候補の多さは性能ではない。使う側の判断の負担として返ってくる。減らす作業は見つける作業と同じくらい大事だった。

消す道具ほど消さない仕組みのほうが大事だと思っている。起動時は必ず安全モードで始まる。安全モードのあいだはボタンを押しても何も消えない。まず何が見つかるかを見てから本番の削除へ進む。削除の前にはバックアップを取る。ファイルとフォルダとレジストリに加えてサービスとタスクの定義まで戻せるようにした。壊れたときに、あった場所へ戻せなければ安心して消せないからだ。

土台は .NET 10 と C# と WPF だ。インストーラーは WiX で作った MSI になる。速いファイル検索には Win32 の USN Journal を使い、MFTを直接読む形にしている。構成は、ロジック本体の Core と画面の UI、テストとインストーラーに分けている。探す仕組みと消す仕組みと画面を分けたのは、探す側の決まりを変えたときに画面まで引きずられないようにするためだ。

作った道具は Purge として公開している。Windows のアプリを消し残しまで含めて片付けたい人の手に渡ればと思っている。
